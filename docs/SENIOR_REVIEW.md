## Загальний вердикт

Проєкт помітно вищий за середній рівень «дослідницького CV-коду»: чиста шарувата структура `src/` (core / models / database / localization / geometry / tracking / workers / gui / network), Pydantic-конфіг, Loguru, ruff + pre-commit, 87 тестів, headless-режим з graceful shutdown по SIGINT, продуманий VRAM-менеджер із pin/prewarm/викиданням за бюджетом. Основні системні ризики — не в стилі, а в **конкурентності**, **контракті конфігурації** та **відсутності CI**. Оцінка: міцні 7/10 з можливістю дійти до 9 за 2–3 тижні цілеспрямованої роботи.

## 1. Архітектура

**Добре:** межі модулів здорові — geometry не знає про Qt, workers спілкуються з GUI лише сигналами, мережа ізольована в `network/` з asyncio-loop в окремому потоці (`coordinates_broker.py:40-60` — грамотний патерн `run_coroutine_threadsafe` для зупинки).

**Проблеми:**

- **MainWindow — God-object через міксини.** `CalibrationMixin` (692 рядки), `DatabaseMixin` (650), `TrackingMixin`, `PanoramaMixin` — усі неявно залежать від десятків атрибутів `self` (`self.database`, `self.calibration`, `self.config`, `self.status_bar`…), які ніде не оголошені як контракт. Це класична пастка: рефакторинг будь-якого атрибута ламає 4 файли без жодної підказки від IDE/mypy. Рекомендація: винести стан у явний `AppContext`-об'єкт (dataclass), який міксини отримують типізовано, або перейти від міксинів до композиції (контролери).
- **Порушення інкапсуляції між шарами:** `calibration_mixin.py:94,245` читає `converter._initialized`, `converter._mode`; `tracking_worker.py:153,227-229` лізе у `video_src._cap` та `localizer._last_state`. Кожен такий доступ — прихований контракт. Дешевий фікс: додати публічні property (`converter.mode`, `localizer.last_state`, `video_src.pos_msec`).
- **`Localizer` (918 рядків) робить забагато:** retrieval + rotation prior + матчинг + RANSAC + Kalman + outlier + FOV + confidence + fallback + мультибазність. Розбити хоча б на `CandidateRetriever` / `PoseSolver` / `TrackState` — інакше кожна зміна ризикує зачепити сусідній етап (що ми вже бачили на практиці).

## 2. Конкурентність — головна зона ризику

У процесі співіснують: Qt event loop, `QThread`-воркери, «голі» `threading.Thread` (prewarm, geo-rebuild), asyncio-loop у потоці. Синхронізації — дві: `geo_aware_retriever._lock` і `model_manager._model_lock`. Цього мало:

- **`DatabaseLoader` не потокобезпечний, але шариться між потоками.** `_feature_cache` (OrderedDict) мутується з GUI-потоку та воркерів без лока; h5py-хендл один. Найгостріше: `CalibrationPropagationWorker._save_to_hdf5` робить `database.close()` → пише → `_load_hot_data()` — якщо в цей час GUI/трекінг викличе `get_local_features`, отримаємо `RuntimeError("Database not opened")` у кращому випадку, сегфолт h5py — у гіршому. Рекомендація: один `threading.RLock` на всі публічні методи DatabaseLoader + явна заборона запуску трекінгу під час пропагації (disable кнопки).
- **Файл конфігу пишеться неатомарно** (`config.py: save_user_config` — прямий `open(w)`), і ми буквально спіймали наслідок: `config/config.py` містив 470 хвостових null-байтів після конкурентного запису. Фікс на 5 рядків: писати у тимчасовий файл + `os.replace()`. Те саме для `calibration.save()` і `project.json`.
- **`stop()`-патерни неоднорідні:** `RealtimeTrackingWorker` чекає 5 с і лише логує, якщо потік не зупинився; `VideoDecodeWorker.wait(1000)` у діалозі. Зомбі-потік з відкритим відеохендлом — реальний сценарій при закритті вікна. Варто уніфікувати: `stop() → wait() → terminate()+log` як останній засіб.

## 3. Надійність та обробка помилок

- **12 широких `except Exception`, з них ~11 «ковтають» мовчки** (`pass`). Найнебезпечніший — `_prefetch_features` у воркері пропагації: будь-яка помилка читання фіч тихо перетворюється на «кадру немає», і граф просто будується без нього. Мінімум — `logger.debug` з frame_id і лічильник пропущених у підсумковому лозі.
- **`config.py` використовує `print` замість logger** (`:406,415`) — повідомлення про зіпсований user_config ніколи не потрапить у файловий лог, а це саме той випадок, який треба бачити.
- **Пастка пріоритету конфігів:** `user_config.json` перекриває дефолти `AppConfig` повністю. Змінюєш дефолт у коді — нічого не відбувається у користувача. Ми на це витратили годину; наступний розробник витратить стільки ж. Рекомендація: при завантаженні логувати diff «user override vs default» + додати merge-стратегію по версії конфігу (config_version + міграції).
- **`test_dll.py`, `test_torch.py` у корені** — debug-скрипти поза `scripts/`, збивають з пантелику (pytest їх намагається зібрати за назвою).

## 4. Типізація і якість коду

- Анотації повернення — у **202 з 524 функцій (~38%)**. Нових модулів це стосується менше (geometry майже повністю типізований), GUI — майже нетипізований. mypy/pyright у проєкті **немає взагалі** — з міксин-архітектурою це подвійно боляче.
- Ruff-набір пристойний (E/W/F/I/N/UP/B), але без `RUF`, `SIM`, `C4`, `ARG`, `PL`-підмножини; `ANN` хоча б для `src/geometry` і `src/calibration` дав би реальний захист.
- Мертві артефакти research-ітерацій: непідключені `histogram_matching`, depth-корекція, GSD (деталі у перф-плані), `GtsamPoseGraphOptimizer`, який фактично завжди делегує в SciPy. Кожен такий шматок — «обіцянка», яку код не виконує; краще видалити або довести.

## 5. Тести і CI

- 87 тестів — гідно для такого проєкту. Юніт-зріз (geometry/config) у чистому середовищі: **24/25 passed**. Але:
- **CI відсутній повністю** (немає `.github/workflows`). Тести, які ніхто не запускає автоматично, деградують: впійманий фейл `test_config_defaults` — тест звіряє літерал `"opencv"` з конфігом, де вже `"poselib"`. Тест-літерали конфігу — антипатерн; звіряти треба інваріанти (тип, діапазон), а не значення.
- **Найризиковіші підсистеми не покриті:** пропагація (граф + оптимізатор), Localizer, DatabaseLoader. При цьому synthetic-тести для них пишуться легко — ми в цій сесії ганяли end-to-end pose graph без GPU (відновлення траєкторії, реакція на хибний loop closure). Ці сценарії треба закомітити в `tests/` як регресійні.
- `conftest.py` містить порожні TODO-фікстури (`sample_image` → `pass`) — фікстура, що повертає None, гірша за відсутню.
- Мінімальний CI: `ruff check` + `pytest tests/ -m "not gpu"` на Linux/Windows матрицях + `pip install -e .` smoke. Півдня роботи.

## 6. Безпека

- **WS (8765) і REST (8080) слухають `0.0.0.0` без автентифікації і TLS** (`ws_server.py:14`, `rest_server.py:10`). Для польового ноутбука в чужій Wi-Fi мережі це відкритий канал телеметрії дрона + керування. Мінімум: дефолт `127.0.0.1`, токен через заголовок, `0.0.0.0` — лише явним прапором з warning-логом.
- **`trust_remote_code=True`** при завантаженні DINOv3 з HuggingFace (`dinov3_wrapper.py:48`) — виконання чужого коду з мережі. Зафіксувати revision (`revision="<commit>"`), щоб підміна репозиторію не стала RCE.
- `torch.hub.load` для DINOv2 — та сама категорія; фіксувати теги.
- Позитив: `parse_combined_gps` на regex (без eval), шляхи через `pathlib`, pickle не використовується.

## 7. Пакування та гігієна репозиторію

- `pyproject.toml` сучасний, `requirements.txt` коректно делегує (`-e .[dev]` + extra-index) — добре. Git-залежність LightGlue запінена комітом — добре.
- **Немає `.gitattributes`** → CRLF-шторми: поточний diff — 183 файли, ~50k рядків «змін», серед яких реальні правки тонуть. Один файл (`* text=auto eol=lf`) вирішує назавжди.
- **У git закомічені `scratch/` (генератори презентацій), `KnowledgeBase/` (Obsidian-нотатки з .obsidian), `logs/`** — це особистий робочий простір, а не код продукту. Винести або хоча б додати в `.gitignore` для нових файлів.
- `requires-python = ">=3.10,<3.12"`, venv на 3.11.9 ✓, але в репо валяються `__pycache__/*.cpython-314.pyc` — хтось запускав 3.14; сліди варто прибрати, а `__pycache__` не комітити (він уже в .gitignore, але старі файли лишилися трекнутими).
- Версія `1.0.0` статична при активній розробці — перейти на `setuptools-scm` або хоча б інкрементити.
